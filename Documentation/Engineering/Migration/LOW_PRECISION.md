# Low-precision Modular decode compatibility

Pinned predecessor `57e81cb9e2411d1efac435b429a306a031744c1e` decodes integer samples from 1 through 16 meaningful bits. SwiftJXL's initial public integration admitted only 8–16, leaving a real compatibility gap. Twenty-eight independently generated libjxl fixtures at 1–7 bits, grey/RGB and optional straight alpha all decode to the exact expected samples in the predecessor. The pre-change successor rejected all twenty-eight.

The decoder and inverse-transform precision guards now admit 1–16 bits. No scaling, quantisation or algorithm change is introduced. Allocating decode still returns UInt16 storage; callers may provide UInt8 storage for 1–8-bit images while preserving `meaningfulBits`. The tests compare every sample in both layouts and require the caller allocation to remain the output owner. They retain the predecessor's unsupported low-precision encoding boundary: encoder capability remains 8–16 bits and such inputs reject rather than silently becoming 8-bit images.

CLI inspection and validation report the true bit depth. NRRD/PNM export still rejects precisions those adapters do not represent under their declared profiles. The focused CLI suite tests all 28 streams, boundary export rejection and direction-specific capability reporting. [Fixture provenance](../../../../Tests/SwiftJXLCoreTests/Fixtures/Modular/LowPrecision/manifest.json) records the generator, baseline commands and exact sample results.

The first extension exposed an additional 8-bit lower bound in inverse transforms: grey streams passed while multi-component streams failed. Widening that reviewed guard fixed the failure without changing transform arithmetic. The corrected unit and CLI results, source hashes and commands are recorded in [validation](Evidence/ModularColour/LowPrecision/validation.json). Previous ICC/high-precision evidence remains scoped to its tested revision; final-head hosted CI and the additional mutation campaign are separate gates.
